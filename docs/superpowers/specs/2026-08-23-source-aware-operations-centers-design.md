# 设计宝多业务来源运营中心改造设计

## 背景

系统已经能从每日 Excel 读取“项目明细2”和“工作表3”，并在指标中心展示设计宝、小红书和全部业务的指标。当前首页、商家中心、项目中心以及商家分类仍使用不区分业务来源的持久化数据，导致四个页面的筛选口径不一致；同一商家在设计宝和小红书中的经营表现也无法分别判断。

本次改造把业务来源、大区、城市和商家统一为全站运营筛选条件，并为每个商家、每个数据日期分别保存设计宝、小红书和全部业务三套分类。项目中心同时把原“商家ID”列改成“装企”，装企名称作为主信息，ID 在下方以小字显示。

## 已确认的业务决策

- 前台提供“设计宝 / 小红书 / 全部业务”三个来源选项，默认进入“设计宝”。
- “全部业务”只合并设计宝和小红书，不包含无法识别的其他来源。
- 全部业务的指标和分类基于两种来源的原始分子、分母及项目集合重新计算，不对两个已计算百分比做平均。
- 同一商家、同一日期保存设计宝、小红书、全部业务三套分类结果。
- “确认 C”和“临时豁免”只作用于用户操作时选中的来源；在“全部业务”下操作时只作用于全部业务分类。
- “永久排除”作用于商家全局，不受来源限制。
- 首页、指标中心、商家中心、项目中心共享同一组筛选条件：业务来源 → 大区 → 城市 → 商家。
- 页面跳转和下钻必须保留筛选条件。
- 项目中心的“装企”列显示装企名称，商家 ID 作为名称下方的辅助小字。
- 上线前对已有成功批次按日期顺序重算，不要求管理员重新上传 Excel。

## 目标

- 四个业务页面使用相同的来源和组织口径，避免同一筛选条件出现不同数字。
- 同一商家可以在设计宝、小红书和全部业务下得到不同且可解释的分类。
- 首页、商家中心和项目中心只读取筛选范围内的最新成功批次数据，不混入历史项目当前态。
- 历史数据完成可重复、可恢复的来源回填与分类重算。
- 已有人工决策、权限范围和审计信息得到保留。

## 非目标

- 本次不新增第三种可选业务来源。“其他”只用于数据追踪和异常排查。
- 本次不修改已确认的 40 个指标名称与计算公式。
- 本次不引入新的任务管理、跟进记录或消息通知系统。
- 本次不把分类规则做成完全可视化配置平台。
- 本次不改变 Excel 只读取“项目明细2”和“工作表3”的约束。

## 术语与来源模型

新增统一枚举 `BusinessSource`：

- `DESIGNBAO`：设计宝。
- `XIAOHONGSHU`：小红书。
- `OTHER`：源文件中无法映射到前两项的来源；只供追踪，不在前台来源选择器中展示。
- `ALL`：设计宝与小红书的综合计算结果，只能用于综合分类和人工决策，不能作为单个项目的真实来源。

导入时使用现有工作簿原始列 F 进行标准化。标准化后的来源必须写入明确字段，后续查询不得继续依赖 `raw` JSON 或 `dimensionKey` 字符串前缀推断来源。

## 数据模型

### 项目快照

`ProjectSnapshot` 新增必填 `businessSource`：

- 每条快照只能是 `DESIGNBAO`、`XIAOHONGSHU` 或 `OTHER`。
- 导入仓储根据标准化结果写入来源。
- 来源感知的首页和项目中心以最新成功批次的项目快照为事实来源，不再直接用跨批次混合的 `Project` 当前表生成运营统计。
- `Project` 仍作为项目身份和关系主表保留，不承担来源筛选事实。

### 指标快照

`MetricSnapshot` 新增必填 `businessSource`，其含义与项目快照一致。现有 `MetricSource` 继续表示指标的数据来源类型或计算来源，不能与业务来源混用。

设计宝、小红书指标快照分别按实际来源保存；全部业务查询通过两类快照的分子和分母合并得出。不得额外保存一个由百分比平均得到的 `ALL` 指标快照。

指标快照唯一约束必须显式包含 `businessSource`，不再以 `dimensionKey` 中的来源前缀充当唯一性的一部分。过渡期可以继续读取旧键，但新写入必须使用无来源前缀的规范维度键。

### 商家分类快照

`MerchantClassificationSnapshot` 新增必填 `businessSource`，允许 `DESIGNBAO`、`XIAOHONGSHU`、`ALL`，唯一约束改为：

```text
(merchantId, dataDate, businessSource)
```

同时新增 `dataAvailable`。`classification` 和 `suggested` 改为可空：`dataAvailable = false` 时两者必须为空，原因固定为“该来源暂无数据”；`dataAvailable = true` 时两者必须有值。数据库约束或仓储校验必须保证这两种状态不能混用。

每次分类任务为有数据的商家生成三套结果：

- 设计宝分类只使用设计宝项目和指标。
- 小红书分类只使用小红书项目和指标。
- 全部业务分类使用设计宝与小红书项目集合以及合并后的分子、分母重新计算。

若商家在某个单独来源完全没有项目，仍保存该来源的无数据快照，以保证每个活跃商家每天有三条来源记录；页面显示“该来源暂无数据”，不凭另一来源的数据生成该来源分类。全部业务只要两个来源之一有数据即可计算。

### 规则命中与人工决策

`RuleHit` 新增必填 `businessSource`，只记录项目的真实来源，不生成重复的 `ALL` 项目预警。唯一约束显式包含业务来源，全部业务页面通过合并设计宝和小红书规则命中得到项目预警列表。

`MerchantOverride` 新增可空 `businessSource`：

- `CONFIRM_C`、`TEMP_EXEMPT` 与既有 `MANUAL_CLASSIFICATION` 必须带来源，可为 `DESIGNBAO`、`XIAOHONGSHU` 或 `ALL`。
- `PERMANENT_EXCLUDE` 的来源为空，表示商家全局生效。
- Worker 计算某来源分类时，只应用相同来源的确认或豁免，再叠加全局永久排除。

所有人工操作继续保留操作人、操作时间、原因和原始审计记录。

## 分类计算

分类规则版本升级为新版本。Worker 处理每个批次时按以下顺序执行：

1. 从该批次项目快照构建设计宝、小红书两个实际来源的数据集。
2. 分别读取对应来源指标快照，计算设计宝和小红书分类建议与证据。
3. 合并两个来源的项目集合、计数、分子和分母，计算全部业务分类建议与证据。
4. 对三个来源分别应用对应人工决策和全局永久排除。
5. 在事务中 upsert 三套分类快照及证据。
6. 只有该批次该日期的三套计算全部成功后，才替换可见结果；失败时保留上一次成功结果。

综合比例的正确形式为：

```text
综合率 = (设计宝分子 + 小红书分子) / (设计宝分母 + 小红书分母)
```

没有有效分母时沿用指标公式既有的空值规则，不显示为 0%，也不参与依赖该指标的分类条件。

## 全站筛选与状态

### 统一筛选器

首页、指标中心、商家中心和项目中心页面顶部使用同一筛选组件和同一状态模型：

```text
业务来源 → 大区 → 城市 → 商家
```

- 默认来源为设计宝。
- 选择大区后，城市列表只显示该大区内且用户有权访问的城市。
- 选择城市后，商家列表只显示该城市、当前来源和最新成功批次中出现的商家。
- 上游条件变化时自动清除已失效的下游选项。
- 来源、大区、城市、商家写入 URL 查询参数，URL 是可分享、可刷新恢复的权威状态。
- 组织和商家参数必须在服务端再次校验权限，不能只依赖前端选项限制。

建议新增通用筛选接口 `GET /api/filters/operations`。既有指标筛选接口在过渡期保留兼容，最终由四个页面统一使用通用接口。

### 参数约定

建议统一参数名：

```text
source=DESIGNBAO|XIAOHONGSHU|ALL
regionId=<organization id>
cityId=<organization id>
merchantId=<merchant id>
```

页面跳转和“查看明细”链接必须原样携带这些参数。无效或越权参数返回 400 或 403，不静默扩大到全国数据。

## 页面设计

### 首页

接口改为：

```text
GET /api/dashboard?source=&regionId=&cityId=&merchantId=
```

查询口径：

- 使用筛选范围内最新成功批次的项目快照。
- 商家总数为筛选后项目快照中的去重商家数。
- 待辅导、未改善和异常项目均从筛选后的项目快照及规则命中计算。
- 商家结构读取所选来源、数据日期不晚于批次日期的最新分类快照。
- 在全部业务下，项目预警合并两个实际来源且按项目业务键去重；商家结构读取 `ALL` 分类快照。

页面右上角显示当前数据日期、来源及组织范围，不再只显示“等待首次上传”。点击统计卡片时跳转到相应商家或项目列表，并保留全部筛选参数和异常条件。

### 指标中心

保留已上线的 40 个指标、多选、趋势和分组矩阵能力，接入全站统一筛选状态：

- 设计宝与小红书读取对应来源指标快照。
- 全部业务按原始分子、分母聚合。
- 日、周、月时间范围继续生效，周定义保持周日到周六。
- 大区、城市、商家与其他三个页面使用相同的组织 ID 和权限校验。
- 已确认的设计宝 8 月 1 日至 8 月 23 日“分派项目数”为 561，作为回归验收基准；不能因历史批次重复或来源混合回到 587。

### 商家中心

接口改为：

```text
GET /api/merchants?source=&regionId=&cityId=&merchantId=&classification=&search=&page=
GET /api/merchants/:id?source=&regionId=&cityId=
```

列表查询口径：

- 商家集合来自筛选范围内最新成功批次的项目快照。
- 项目数按所选来源去重计算；全部业务合并设计宝和小红书。
- 最后分派时间、SOP 达标率、异常项目数均按所选来源计算。
- 分类和分类变化读取所选来源的分类快照。
- 人工决策按钮明确显示当前作用来源；永久排除需再次提示“将影响全部业务来源”。

商家详情页沿用当前来源，展示对应来源的分类原因、辅导、改善、指标趋势和项目明细。切换来源时重新读取详情数据，不沿用上一来源的分类证据。

### 项目中心

接口改为：

```text
GET /api/projects?source=&regionId=&cityId=&merchantId=&abnormal=&coached=&improved=&page=
GET /api/projects/:id?source=&dataDate=
```

查询口径：

- 项目列表来自筛选范围内最新成功批次的项目快照。
- 设计宝和小红书只显示相应真实来源；全部业务合并两类来源。
- 异常、需辅导、是否辅导和是否改善筛选在来源过滤之后执行。
- 项目详情读取列表对应的数据日期和来源快照，避免展示跨批次的项目当前态。

列表字段中的“商家ID”改为“装企”：

```text
装企名称
merchant-id（小字号、次要颜色）
```

API 必须返回 `merchantName` 和 `merchantId`。缺失名称时主行显示“未匹配装企”，ID 仍保留，便于管理员排查数据匹配问题。

### 空状态与重算状态

筛选条件没有数据时，四个页面统一显示：

```text
当前筛选范围暂无数据，请调整业务来源或组织范围。
```

历史重算期间显示非阻断横幅，包括当前进度、最后成功数据日期和失败批次数。页面继续展示最后一次成功结果；不得用未完成或部分重算结果覆盖线上数据。

## API 与权限

- 所有来源感知 API 必须验证 `source` 枚举，默认仅限前台请求为 `DESIGNBAO`。
- `OTHER` 不接受为普通前台查询参数，只允许管理员诊断接口使用。
- 区域负责人只能访问授权大区及其城市、商家；城市负责人只能访问授权城市及其商家。
- `merchantId` 必须同时属于所选组织范围和当前用户权限范围。
- 全部业务查询是两个允许来源的合并，不得绕过任一来源下的组织权限。
- 返回错误信息不得包含数据库连接串、对象存储密钥或原始堆栈。

## 历史迁移与重算

### 数据库迁移

1. 添加 `BusinessSource` 枚举和各表来源字段，初始允许为空以完成回填。
2. 项目快照从原始列 F 回填来源，无法识别的标记为 `OTHER`。
3. 指标快照从现有维度键和已保存上下文回填来源，回填完成后停止使用隐藏前缀查询。
4. 现有商家分类快照迁移为 `ALL`，作为原系统综合口径的临时历史值。
5. 现有非永久人工决策迁移为 `ALL`；永久排除迁移为来源为空的全局决策。
6. 建立新的唯一约束和索引，再将必须字段改为非空。

人工确认过的历史分类记录不直接删除。其审计信息保留为 `ALL` 来源记录；新规则重算更新系统建议与证据，并继续由来源明确的人工决策决定最终分类。

### 历史重算

- 找出所有成功上传批次，按数据日期和创建时间顺序入队重算。
- 已有项目和指标快照足够时直接重算，不要求重新上传对象存储文件。
- 每个批次重算必须幂等；重复执行不能产生重复分类、预警或指标快照。
- 不能使用只跳过冲突的写入掩盖旧错误值，应使用 upsert 或事务内替换系统生成结果。
- 单个批次失败时记录批次、阶段、来源和安全错误原因，继续保留旧成功数据，并允许管理员单独重试。
- 历史重算全部完成后再把四个页面的默认查询切换到新来源字段，避免迁移窗口出现空白页面。

## 部署顺序与回滚

采用兼容性部署：

1. 先上线只增加字段和索引的数据库迁移，旧代码仍可运行。
2. 上线写入新来源字段、三套分类和通用筛选接口的 Worker 与 Web。
3. 执行历史回填和重算，观察批次状态及抽样数据。
4. 数据验收通过后切换首页、商家中心、项目中心到来源感知查询。
5. 稳定后移除对旧维度前缀和混合当前表查询的兼容路径。

若重算或新查询异常，回滚前端查询开关并继续展示旧成功结果；添加式字段和历史审计记录无需删除。任何回滚不得删除上传批次、人工决策或项目快照。

## 测试策略

### 数据模型与迁移

- 同一商家、同一日期可以且只能各有一条设计宝、小红书和全部业务分类。
- 项目快照与指标快照来源回填正确，未知值进入 `OTHER`。
- 旧人工决策按规则迁移，永久排除保持全局。
- 迁移和历史重算重复执行保持幂等。

### Worker 与业务规则

- 同一商家可因两个来源表现不同得到不同分类。
- 全部业务使用合并分子和分母，而非两个百分比平均。
- 单来源无数据时不生成伪分类，全部业务仍可使用另一来源计算。
- 确认 C 与临时豁免只影响选中来源，永久排除影响三个分类。
- 规则命中只保存真实项目来源，全部业务列表不会重复预警。
- 重算失败不替换最后成功结果，并输出可定位的结构化日志。

### API、权限与页面

- 首页、商家、项目和指标接口对同一来源与组织筛选返回一致范围。
- 大区、城市、商家级账号无法通过修改 URL 越权。
- 所有下钻链接保留来源、大区、城市和商家参数。
- 项目列表显示装企名称并在下方显示 ID。
- 空状态和历史重算横幅在相应条件下正确显示。
- 来源或上游组织变化会清除无效下游条件。

### 数据验收与回归

- 使用 `非深圳【设计宝、小红书】.xlsx` 验证设计宝 2026-08-01 至 2026-08-23 分派项目数为 561。
- 分别抽样至少三个商家，核对设计宝、小红书和全部业务的项目数、SOP 指标与分类证据。
- 完整单元测试、集成测试、端到端测试、TypeScript 检查、ESLint 和 Next.js 生产构建全部通过。
- Railway Web、Worker 和 PostgreSQL 健康；历史重算状态可见且没有失败批次。

## 成功标准

- 四个中心均可按设计宝、小红书、全部业务以及大区、城市、商家筛选。
- 四个中心在相同筛选条件下使用同一最新成功批次和同一商家、项目范围。
- 同一商家每天存在可追溯的三套来源分类，人工决策作用域符合已确认规则。
- 设计宝 8 月分派项目数保持 561，来源切换不会混入另一来源或历史重复数据。
- 项目中心“装企”列按名称主显示、ID 辅助显示。
- 历史重算可恢复、可重试、幂等，失败不会破坏已成功数据。
