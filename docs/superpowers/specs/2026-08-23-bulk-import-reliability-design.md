# 设计宝批量导入可靠性修复设计

## 背景

当前真实工作簿在校验后可产生 2,026 条有效项目记录。导入仓储会在一个数据库事务中按记录顺序执行组织、商家和项目的逐条 upsert，总计约 8,100 次顺序数据库操作。事务超时为 120 秒，生产环境可能无法在时限内完成。

当 Worker 执行异常时，任务失败状态只写入 `Job`；`UploadBatch` 仍停留在 `PROCESSING`，Worker 日志也没有输出异常。上传页面只在 React 内存中保存批次编号，刷新后无法恢复最近批次。因此用户看到的结果是长期 `PROCESSING / 0`，刷新后处理结果消失，首页继续显示空数据。

## 目标

- 真实工作簿的 2,026 条有效记录能在 Railway 生产环境完成导入。
- 数据库写入次数从逐行数千次降低为有限数量的批量操作。
- Worker 异常必须同步到上传批次，并在 Railway 日志与上传页面可见。
- 上传页面刷新后自动恢复最近一次批次的状态与结果。
- 失败批次不覆盖已经成功的数据，重复执行保持幂等。

## 非目标

- 不在本次改造中实现精确到每一行的实时进度条。
- 不拆分成多级分布式队列或增加新的基础设施服务。
- 不修改指标、商家分类和项目预警业务规则。
- 不改变工作簿只读取“项目明细2”和“工作表3”的约束。

## 方案选择

采用“批量写入 + 失败闭环 + 最近批次恢复”。不采用单纯延长事务超时，因为数据继续增长时仍会复现；暂不采用多段队列，因为当前 MVP 数据量不需要额外的调度复杂度。

## 架构与数据流

1. Web 接收 Excel，写入对象存储，创建 `UploadBatch` 和 `IMPORT` Job。
2. Worker 领取 Job，将批次标记为 `PROCESSING`，读取并解析 Excel。
3. 校验器生成有效记录和警告；缺少关键 ID 或无法匹配组织的行继续按已确认规则跳过。
4. Worker 将记录转换为去重后的组织、商家、项目和项目快照集合。
5. 仓储在一个事务中按依赖顺序批量写入：组织 → 商家 → 项目 → 原始行/警告 → 项目快照 → 后续 Job → 批次统计。
6. 事务成功后，`UploadBatch` 更新为 `SUCCEEDED`；后续指标和规则 Job 继续执行。
7. 事务或解析失败时，Worker 记录结构化错误；Job 重试耗尽后把 `UploadBatch` 更新为 `FAILED`。
8. 上传页面加载时请求管理员最近一次批次，并继续轮询未结束批次。

## 批量写入设计

### 数据准备

- 组织按完整路径去重，确保全国、大区和城市父子关系稳定。
- 商家按 `merchantId` 去重，以工作簿中最后一条有效记录作为本批次的名称和所属城市值。
- 项目按 `assignmentId` 去重，以最后一条有效记录作为本批次的当前字段值。
- 项目快照仍按数据日期和项目保持唯一，重复执行不得产生重复快照。

### 数据库操作

- 组织、商家和项目使用参数化的 PostgreSQL 批量 upsert，按固定大小分块，避免 SQL 参数数量过大。
- 原始行、警告、快照和后续 Job 使用 Prisma `createMany`；支持的表继续使用 `skipDuplicates` 保证重试幂等。
- 每个分块默认不超过 250 条；该值足以显著减少往返次数，同时远低于 PostgreSQL 参数上限。
- 所有批量 SQL 必须通过 Prisma 参数化模板构造，不拼接来自 Excel 的原始字符串。
- 保留单个事务的原子性；事务超时维持 120 秒，避免用延长超时掩盖低效写入。

## 失败状态与日志

- Worker 领取、开始、成功和失败时输出包含 `jobId`、`batchId`、`jobType`、`attempt` 的结构化日志。
- 单次执行失败后保留现有退避重试逻辑。
- 当 IMPORT Job 达到最大重试次数时，同时更新对应 `UploadBatch`：
  - `status = FAILED`
  - `failureStage = WORKER`
  - `failureMessage` 保存适合管理员查看的简短错误信息
  - `finishedAt` 写入失败时间
- 上传状态接口返回失败阶段和安全的失败提示，不返回数据库连接串、对象存储密钥或完整堆栈。
- 上传页面显示中文失败提示，并引导管理员查看日志或重新上传；不再将失败批次持续展示为处理中。

## 刷新恢复

- `GET /api/admin/uploads` 返回当前管理员可查看的最近一次上传批次；MVP 管理员具有全国权限。
- 上传组件首次加载时调用该接口：
  - `QUEUED` 或 `PROCESSING`：立即展示并继续轮询。
  - `SUCCEEDED` 或 `FAILED`：展示最终统计和问题明细，不继续轮询。
  - 没有历史批次：保持当前空白上传表单。
- 页面内仍使用批次详情接口轮询，轮询间隔保持 1.5 秒。

## 幂等与数据安全

- 文件哈希与数据日期继续用于识别完全相同的上传。
- 批量 upsert 使用业务主键，任务重试不会生成重复商家或项目。
- 项目快照使用既有唯一约束，任务重试不产生重复日快照。
- 只有完整事务成功后才把批次标记为成功；失败事务不留下半批业务数据。
- 现有成功批次不会被失败批次删除或覆盖。

## 测试策略

- 单元测试：组织、商家和项目去重及分块边界。
- 仓储集成测试：批量 upsert、重复执行幂等、事务失败回滚。
- Worker 测试：执行失败会记录错误；重试耗尽会把批次更新为 `FAILED`。
- Web API 测试：最近批次查询、失败信息脱敏、权限校验。
- UI 测试：刷新后恢复处理中/成功/失败批次并正确轮询。
- 真实工作簿验收：保持 2,026 条成功、89 条跳过的预期结果。
- 回归验证：完整测试、八个 TypeScript 项目检查、ESLint 和 Next.js 生产构建全部通过。

## 上线与验收

1. 代码推送后等待 Railway 的 Web 和 Worker 均部署成功。
2. 管理员重新提交 `2026/08/23` 的原工作簿一次。
3. 上传页面刷新后仍能看到该批次，并最终显示成功/跳过/警告统计。
4. 首页、商家中心和项目中心能读取已导入数据。
5. 若导入失败，上传页面必须显示 `FAILED` 和可操作提示，Worker 日志必须包含对应批次错误。

## 成功标准

- 真实工作簿导入不再因逐条写入超过事务时限。
- 生产导入在 5 分钟内得到明确的 `SUCCEEDED` 或 `FAILED` 结果。
- 任意刷新或重新进入上传页面都能看到最近批次状态。
- Railway 日志能够通过批次编号定位导入失败原因。
