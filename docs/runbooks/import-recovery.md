# Excel 导入失败恢复手册

## 正常导入

1. 管理员进入“管理后台 → 数据上传”。
2. 选择数据日期和 `.xlsx` 文件。
3. 系统只读取 `项目明细2` 与 `工作表3`；其他子表不会入库。
4. 页面显示“导入成功”后，再检查首页的数据更新日期。

上传后先保存原文件，再异步校验。只有整批没有阻断错误时，项目、指标和预警才会成为最新正式数据；失败批次不会覆盖上一次成功结果。

## 状态判断

- `QUEUED`：已接收，等待处理。
- `PROCESSING`：正在解析或计算。
- `SUCCEEDED`：项目、指标和规则均可继续处理。
- `FAILED`：当前批次不生效，查看错误代码后修正源文件。

## 阻断错误

| 错误代码 | 含义 | 处理方式 |
|---|---|---|
| `MISSING_ID` | 项目 ID 或商家 ID 缺失 | 回到对应行补齐稳定 ID |
| `DUPLICATE_PROJECT_ID` | 同批次“项目 ID + 商家 ID”重复 | 保留一条正确记录或修正 ID |
| `INVALID_DATE` | 分派时间无法识别 | 改为合法日期 |
| `UNKNOWN_ORGANIZATION` | 城市在 `工作表3` 找不到唯一大区 | 补充/修正城市映射 |
| `INVALID_ENUM` | 是/否等字段出现非法值 | 改为数据字典允许值 |

`OPTIONAL_VALUE_MISSING` 是警告：原值会保留，标准字段按空白处理。空白、否和 0 不会合并。

## 当前真实文件的已知问题

对 `非深圳【设计宝、小红书】.xlsx` 的只读验收发现：共解析 2065 条项目分派；存在 99 条 ID 缺失和 2 条未知组织映射（张家港市，对应源表第 1545、1546 行），另有 509 条可选字段警告。修正这些阻断项后，应重新上传修正版文件。原文件不需要、也不应被系统修改。

## 卡住或失败时

1. 等待 2 分钟并刷新批次状态；不要连续重复上传同一文件。
2. 查看 Worker 日志：`docker compose --env-file .env.production -f infra/production/docker-compose.yml logs --since=15m worker`。
3. 若 Worker 已停止，先确认 PostgreSQL、MinIO 健康，再重启 Worker。
4. 同一批次作业可安全重试；快照有唯一约束，不会重复生成。
5. 修正后的文件哈希不同，可以用相同数据日期重新上传。

不要直接删除失败批次、原始行或错误记录；它们是导入审计依据。

## 业务来源历史重建失败

`pnpm rebuild:business-source` 是幂等命令。若执行中断、某批失败或 Worker 重启，先保留 `SOURCE_AWARE_OPERATIONS_ENABLED=false`，确认 PostgreSQL 与 Worker Online，然后在 Railway 一次性 Shell 中重新运行同一命令。系统只补齐未完成的来源标签、指标和规则结果，不需要重新上传 Excel。

等待重建状态满足 `completed = total`、`failed = 0` 后，再验收设计宝 `2026-08-01..2026-08-23` 的“分派项目数”为 `561`，并分别抽查设计宝、小红书、全部业务。验收通过前不得切换 Web 到来源感知查询。

恢复过程中永远不要删除已上传批次、项目快照、人工商家决策或审计日志。若重试仍失败，应保留失败记录和最后一版成功数据，先将 Web 查询开关维持或回退到 `false`，再根据失败批次和 Worker 日志修复。
